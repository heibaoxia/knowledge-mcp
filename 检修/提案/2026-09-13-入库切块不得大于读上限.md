# v6：检索与结构解耦 + 迭代检索（给判断的料，不给判断）

日期：2026-09-13
状态：v5，设计已收敛，待开工
规格：以 `需求.md` 为准。本文是提案，通过后先改说明书再改代码。

## 1. 现状为什么"不完全"

因为现在的设计把**结构（标题层级）**当成了检索的入口。整条链路都建立在一个假设上：

> 标题层级是可靠的、有意义的、并且恰好等于"内容单元"。

而真实 Markdown 文案的结构分四种，现状只在第一种成立：

| 类型 | 例子 | 现状 | 
|---|---|---|
| A 结构在，层级也合用 | 心理学与生活（h1章+h2/h3节） | 能用 |
| B 结构在，但没有子层级、单元太大 | 自卑与超越（只有 16 个 h1，每章 1～2 万字） | 只能硬切，块名重复 |
| C 结构没被解析出来 | 「第一章 …」被 markitdown 吐成普通文本 | **整个失效** |
| D 完全没有结构 | 一堆无标题长文/笔记 | **整个失效** |

毛选是 A 的变种：结构在，但 h1=卷（20～37 万字），切块只认 h1 → 394 篇被吞掉。

**症结：结构一旦不可靠，"能不能找到"就跟着一起垮。** 结构不该有这么大的权力。

## 2. 更好的办法：把三条保证拆开

| 要保证的 | 靠什么 | 与结构的关系 |
|---|---|---|
| **读得到**（块能被读完） | 每块 ≤ 4000 字 | **无关** |
| **搜得到**（任何词都能找到） | 正文全文索引，只回身份不回正文 | **无关** |
| **导航顺**（路标和续读好看） | 块名 = 书里的标题；邻块索引 | 有关，但只是锦上添花 |

**一句话：结构只用来"命名和导航"，不用来"决定能不能被找到"。**

这样切块策略就不再是单点故障——**就算切得不好，也还搜得到，只是读起来不顺**。现在是切坏了就彻底瞎。

## 3. 切块：一套算法，四级降级

不管有没有目录，都走这一条路：

1. 有标题 → 从浅到深下沉，直到节点 ≤ 4000 字（只切超大的，不撕碎正常的节）
2. 沉到底还超，或压根没标题 → **按段落贪心打包到 ≤ 4000 字**（不是死板地每 4K 一刀，永远落在段落边界上；只有单个段落自己就超 4000 才在句子上断）
3. 中文结构行兜底：整行 ≤40 字、以「第X章/第X节/一、/（一）/壹、」开头、行尾无 `。！？` → 当结构用（**只用于切分和命名，正文不改一字**）
4. 命名：自己的标题 → 最近上级标题 +（i/n）→ 该块第一句前 20 字

**块大小 = 4000 字**。依据（实测）：4K 压在大多数书的自然单元中位之上（毛选 1687、心理学与生活 1186），只切超大块不撕结构；且 5 × 4K = 20K ≤ 24K 整次总顶，一次能读满 5 块（若块是 8K，5×8K=40K 超顶，"最多 5 块"等于作废）；命中一个块只付 4K 上下文。

## 4. 检索：正文全文索引，进程内、不落盘

- **SQLite FTS5**（Python 标准库自带，已验证 3.42 + `bm25()` + 列权重，**零新依赖**）
- 中文**不上 jieba**：沿用代码里已有的"连续汉字二字片"（`retrieve.py` 的 `_tokens`），入库切二字片流，查询同样展开 → 2 字问句也能命中
- 列权重：标识(0) / 块名(3.0) / 正文(1.0)
- **索引不落盘**：进程内建，首次检索建一次并缓存。实测 337 万字：分词 0.9s + 建索引 1.6s = **2.5s**，一次查询 **4ms**
- **正本永远只有 Markdown**；硬盘上不多任何文件，数据库里不存知识
- **导航块降权**：实测搜「矛盾论」第一名是 `01-目 录`（那页列着全部篇名，会霸榜）。这类链接行占比高的块只按块名进索引，正文不进索引，**内容照旧可读不删**
- 路标仍最多 5 条、每条最多 3 个建议块、**无正文**

**规模阈值**：340 万字 = 2.5s 可接受；到千万字量级要改落盘索引（仍是派生物，正本地位不变）。

## 5. 顺带：笔记一起吃这套

笔记本来就是单块文档 → 正文进索引 → 找得到。现状笔记只能靠标题/标签碰运气。

## 6. 红线：只改一处措辞

- 「不把知识存进数据库」**原封不动**（索引进程内不落盘，硬盘上没有索引文件）
- 「检索只扫抬头，不打开正文」→ **「检索只回身份和命中理由，永不回正文；正文只在入库建索引和点名阅读时打开」**。实质不变：路标里一个字的正文都没有，Agent 仍必须点名才能读，单块/整次/块数顶一条不动

## 7. Agent 自己决定要不要继续

阅读**仍点名、仍无状态**，**不引"翻页游标"**。每次阅读末尾附一行邻块索引（只有块名，无正文）：

```
邻块：上一块 书/1-7/矛盾论（1/2）｜下一块 书/1-7/矛盾论（2/2）
```

## 7.5 迭代检索：给判断的料，不给判断

现状：Agent **已经**可以任意多次调检索/阅读（无次数限制、无状态）。缺的不是"能继续"，而是**判断该不该继续所依据的信息**。

加两样，都是抬头级、都不含正文：

1. **命中分布**——路标里报"命中 47 块，分布：第一卷 6 ｜ 第二卷 21 ｜ …"。让 Agent 分得清"库里只有一处提到"和"库里 47 处提到"。**这是"要不要继续"唯一可依据的事实。**
2. **已读标记**——路标上标 `[已读]`，数据来自已有的 `检修/calls.jsonl`（写笔记求证已经在用这套日志），窗口与求证一致（最近 100 条 / 24 小时）。防同一块被反复读。

**红线：不给"够了"的信号。** 工具只报"还有多少"，**绝不替 Agent 说"你读够了"**——那是判断，归 Agent。这跟"代码焊步骤、Agent 干活"是同一条线。

**新风险（已进验收）**：分布信息可能诱发"还有 47 块没看"的焦虑，反而多找。所以 Q11 克制题进红线：关键词命中 524 次、答案只在一篇，必须 ≤4 块、≤2 轮。

不引翻页游标、不引会话内隐藏状态。

## 8. 其余已定

单次 5 块 / 单块顶 8000（兜底，正常不触发）/ 整次顶 24000 **不动**；导读只留顶层目录当小地图；原书目录页内容不删；旧书（被讨厌的勇气 5 章超 8K）一并重切。

## 9. 验收闸门（pytest）

- 嵌套标题 + 超长段落：入库后**每块 ≤ 4000 字**
- **无标题的书**（纯段落流）也能切、能搜到
- 中文结构行（`###` 缺失的「第一章 …」）能当切点
- 检索「矛盾论」命中并给出建议块；扁平 h1 书不退化
- **检索输出里不出现正文句子**（埋一句独有的话，断言不在路标里）
- 导航块不霸占第一名；索引重建两次结果一致
- **硬盘上不出现索引文件**
- 现有 `test_ingest*.py` / `test_retrieve.py` 全绿

线上实测：重切 4 本后，检索「矛盾论」→ 命中 → 点名 → 拿到全文 → 按邻块索引续读。
