## 1. 已知 Spec（需求汇总）

### 1.1 产品定位

一个面向建筑设计的 AI 专家 Agent，以 **Web 聊天界面** 交互，后端由 LLM（DeepSeek-V4）+ 知识库驱动，覆盖建筑设计的完整工作流。

### 1.2 核心能力

| 能力 | 说明 | 优先级 |
|------|------|--------|
| 建筑规范咨询 | 联网实时搜索最新建筑规范/标准，保证时效性 | **P0** |
| 项目知识库 | 用户自有项目按结构化格式存储，LLM 可读取项目现状 | **P0** |
| 设计方法论积累 | 每个项目实践沉淀设计理念，随项目数增长持续更新 | **P1** |
| 成果复用 | 过往项目的效果图排版、文本格式、汇报结构，可被新项目参考复用 | **P1** |
| 建筑设计各阶段辅助 | 覆盖方案设计 → 初步设计 → 施工图阶段的顾问能力 | **P0** |

### 1.2.1 已确认的 Agent 工具

| 工具 | 说明 | 优先级 |
|------|------|--------|
| `websearch` | 接入 Tavily Search API，用于实时联网搜索建筑规范、标准、案例和设计前沿知识 | **P0** |
| `calculator` | 根据用户提供的数字做建筑指标计算：面积配比、容积率、停车数、日照间距等 | **P1** |
| `doc_reader` | 读取用户上传的 PDF/Word/Excel/PPT/Markdown/TXT，抽取文字和表格信息 | **P1** |

> MVP 不包含图纸解析工具。建筑图纸和模型的理解依赖后续多模态 LLM 能力，当前阶段建筑信息主要通过文字描述和文档传递。

### 1.2.3 Agent 对话行为规范

Agent 的对话方式不是简单的一问一答，而是**追问 → 记忆 → 分析 → 给出结论**的递进式对话。

#### 核心原则

| 原则 | 说明 |
|------|------|
| 主动追问 | 用户提问后，先判断自己缺少哪些关键参数，**主动向用户追问**，不要在不了解完整情况时直接给答案 |
| 单次聚焦 | 每次只追问最关键的 1-2 个缺失信息，不要一次抛出大量问题 |
| 边问边记 | 用户回答的每一个信息都要记住，在后续分析中体现出来 |
| 绝不重复 | **永远不要重复询问用户已经回答过的信息** |
| 信息够即答 | 当获取到足够信息时，开始给出分析结论，并附上规范依据 |
| 坦诚边界 | 如果当前信息确实不足以给出可靠判断，明确告诉用户还需要什么，而不是强行给模糊答案 |

#### 对话示例

```
用户：1.5m的走廊是否满足疏散条件？

Agent：需要先确认几个信息：这个走廊在什么类型的建筑里？在哪个楼层？

用户：医院，三层。

Agent：收到。医院门诊楼走道净宽最少1.6m（《综合医院建筑设计规范》GB 51039），
      1.5m不满足。而且三层的话，还要看疏散人数——这个走道大概服务多少人？
      人多的话宽度要求还会更高。

用户：大概100人左右。

Agent：100人按百人指标1.0m算，实际需要1.0m疏散宽度，但医院走道净宽底线1.6m，
      1.5m仍然不满足。建议调整到1.6m以上，同时确认防火分区和最近的安全出口距离。
```

#### 信息记忆要求

Agent 在对话中收集的项目信息应在当次对话中持续记住，包括但不限于：

- 项目城市/地区
- 建筑类型和功能
- 建筑规模和层数
- 用地条件和周边环境
- 用户提到的特殊约束

如果后续引入项目管理和记忆模块，这些信息将持久化存储并在跨对话中复用。

### 1.2.2 MVP 角色定义：建筑专家顾问

第一版 Agent 的核心定位是一个**通晓建筑全领域的通才型顾问**，体验要求如下：

| 能力维度 | 具体要求 |
|----------|----------|
| 规范法律 | 通晓一切建筑相关法律法规、国家标准、地方规范，联网搜索保证时效 |
| 设计院知识 | 覆盖设计院运营流程、出图标准、图纸校审、各专业协调等实践知识 |
| 设计阶段 | 熟悉方案设计 → 初步设计 → 施工图设计各阶段工作内容和交付要求 |
| 整体视角 | 从项目全局出发，而非只看单一专业或单一问题 |
| 风险预判 | 在用户提问时主动识别潜在风险并提前提醒 |

用户使用感受应为：

> 它不只是回答问题，而是像一个经验丰富的建筑总工，能站在整体角度考虑问题，提前给出风险提醒。

通俗说：一个懂全部规范、做过无数项目、知道每个阶段该干什么、并且习惯提前预警的建筑老法师。

**MVP 范围确认**

| 包含 | 不包含 |
|------|--------|
| Web 聊天界面 | 项目管理 |
| DeepSeek-V4 驱动的建筑专家 System Prompt | 项目文件夹读取 |
| `websearch` 工具（联网搜规范） | 多项目切换 |
| 单轮/多轮对话 | 建筑基本信息自动抽取 |
| 流式输出 | 过程文件管理 |
| | Agent 记忆 |
| | 文件上传 |
| | 多模态 |

MVP 阶段只做一个"建筑专家对话"。后续迭代逐步加入项目管理、文件读取、记忆等能力。

### 1.3 未来扩展（非 MVP）

| 能力 | 说明 |
|------|------|
| 多模态审图 | 上传平面图/立面图 → LLM 视觉分析 → 审查意见 |
| 图纸生成 | 平面图 → AI 生成效果图/立面图/3D 模型 |
| 实时协作 | 多人在同一项目上协作 |

### 1.4 知识策略

```
┌─────────────────────────────────────────────────────┐
│                    Agent 知识体系                      │
├──────────────┬──────────────────┬────────────────────┤
│  本地项目库    │   联网实时搜索     │   输出模板库         │
│  (项目结构化)  │   (建筑规范)      │   (成果复用)         │
├──────────────┼──────────────────┼────────────────────┤
│  稳定增长     │   始终最新        │   可参考/可定制       │
│  按项目迭代   │   零本地维护      │   从旧项目提取        │
└──────────────┴──────────────────┴────────────────────┘
```

- **建筑规范/标准**：100% 联网搜索，不做本地存储，保证时效性
- **用户项目**：本地结构化存储（项目元信息 + 关键文档），供 LLM 读取上下文
- **设计成果模板**：从已完成项目中提取排版/格式/汇报结构，供复用

### 1.4.1 项目基本信息策略

每个建筑项目需要维护一份“建筑基本信息”，形式接近标准 **经济技术指标表**。

这份信息不要求用户一次性手动填写完整，而是由系统尽量从项目文件夹中自动获取：

- 用户上传或放入项目文件夹的任务书、说明文本、表格、汇报文件、图纸说明等，都可以作为信息来源
- LLM 负责从这些文件中抽取项目名称、地点、用地面积、建筑面积、容积率、建筑密度、绿地率、限高、功能组成等信息
- 允许部分字段为空，因为很多指标只有在设计逐步推进后才会完善
- 后续对话、上传文件或生成成果时，系统可以持续更新这份项目基本信息
- 抽取出的信息需要保留来源线索，例如来自哪个文件或哪次对话，方便用户核对

通俗理解：项目基本信息不是一张必须先填完的表，而是一个会随着项目进展自动变完整的“项目档案”。

建议初始字段包括：

| 分类 | 字段示例 | 是否允许为空 |
|------|----------|--------------|
| 项目识别 | 项目名称、项目编号、建设单位、设计阶段 | 是 |
| 区位信息 | 城市、区县、基地位置、气候区 | 是 |
| 用地指标 | 用地面积、建设用地面积、道路红线、用地性质 | 是 |
| 建筑规模 | 总建筑面积、地上建筑面积、地下建筑面积、计容面积、不计容面积 | 是 |
| 控制指标 | 容积率、建筑密度、绿地率、建筑高度、限高、停车数量 | 是 |
| 功能组成 | 住宅、商业、办公、酒店、公共配套、地下车库等功能面积 | 是 |
| 设计约束 | 退线要求、日照要求、消防要求、甲方重点要求、规划条件 | 是 |
| 当前状态 | 当前设计阶段、已完成内容、当前待解决问题 | 是 |

### 1.4.2 项目文件夹结构

每个项目使用固定目录结构管理资料，但允许目录为空。目标是尽量贴合实际工作习惯，同时让 Agent 能稳定读取项目上下文。

推荐结构：

```text
projects/
  项目名称/
    00_project_info/        # 项目基本信息、经济技术指标、系统抽取结果
    01_input/               # 原始输入资料：任务书、甲方需求、规划条件
    02_drawings/            # 图纸：CAD、PDF、图片等
    03_references/          # 参考案例、竞品分析、设计灵感
    04_working/             # 过程文件：草稿、阶段性方案、分析图
    05_outputs/             # 最终输出：文本、汇报PPT、效果图、报告
    06_agent_memory/        # Agent 对这个项目的总结、决策、待办、对话摘要
```

### 1.4.3 过程文件与最新版本识别

实际工作中允许用户按简单日期文件夹存放过程文件，例如：

```text
02_drawings/
  CAD/
    0413/
    0420/
    0501/
```

也推荐使用更清晰的日期格式：

```text
02_drawings/
  CAD/
    2026-04-13/
    2026-04-20/
    2026-05-01/
```

处理规则：

- 用户只需要按日期或版本文件夹放入最新项目文件，不要求手动维护索引
- Agent 需要自动扫描项目文件夹，识别最新的项目文件和最新版本目录
- Agent 识别最新版本后，自动生成或更新 `current.md`
- `current.md` 用于记录当前有效版本、主要文件、识别依据、更新时间和需要用户确认的疑点
- 如果同一天存在多个版本，Agent 应根据文件修改时间、文件名关键词（如“最终”“汇报”“修改”“临时”）和用户对话判断当前有效版本
- 如果 Agent 无法可靠判断哪个版本有效，应明确提示用户确认，而不是直接覆盖结论
- Agent 默认优先读取 `current.md` 指向的当前版本；没有 `current.md` 时，才按文件夹日期和文件修改时间推断
- 历史版本不删除，用于方案对比、复盘和成果复用

`current.md` 示例：

```md
# CAD 当前版本

当前版本：2026-05-01
识别依据：该目录日期最新，且包含最近修改的总平面和首层平面文件
主要文件：
- 总平面.dwg
- 首层平面.dwg
- 地下车库.dwg

上一版本：2026-04-20
更新时间：2026-05-01 18:30
待确认：未发现明确“正式版/汇报版”标识，是否以 2026-05-01 作为当前有效版本？
```

### 1.4.4 支持的项目文件类型

系统需要支持读取建筑项目中常见文件类型，并尽量从文件中抽取可供 Agent 理解的信息。

#### MVP 阶段需要支持

| 类型 | 常见格式 | 处理目标 |
|------|----------|----------|
| 文档 | `.pdf`、`.docx`、`.md`、`.txt` | 抽取任务书、设计说明、会议纪要、规范条文、汇报文本 |
| 表格 | `.xlsx`、`.xls`、`.csv` | 抽取经济技术指标、面积表、房间表、功能配比 |
| 演示文件 | `.pptx` | 抽取汇报结构、标题、说明文字、图片页信息 |
| 图片 | `.jpg`、`.jpeg`、`.png`、`.webp` | 作为效果图、分析图、图纸截图、参考图存档；后续多模态分析使用 |
| CAD 图纸 | `.dwg`、`.dxf`、`.pdf` 图纸 | MVP 先做文件识别、版本管理、索引和人工引用；后续逐步增强内容解析 |

#### 后续扩展支持

| 类型 | 常见格式 | 处理目标 |
|------|----------|----------|
| SketchUp 模型 | `.skp` | 识别模型版本、关联效果图/导出图，未来支持模型信息读取 |
| Rhino 模型 | `.3dm` | 识别模型版本、关联参数化设计文件，未来支持几何/图层信息读取 |
| Grasshopper 文件 | `.gh`、`.ghx` | 记录参数化逻辑与设计过程，未来支持参数说明抽取 |
| BIM / Revit | `.rvt`、`.ifc` | 后续用于构件、面积、楼层、专业信息读取 |

#### 处理原则

- 先保证“能识别、能索引、能关联项目上下文”，再逐步增强“能理解文件内容”
- 文档、表格、文本类文件优先做内容抽取和结构化
- CAD、模型类文件初期不强求直接解析几何内容，先纳入版本管理、文件索引和上下文引用
- 对无法直接解析的文件，允许通过导出的 PDF、图片、说明文档辅助 Agent 理解
- 后续多模态能力成熟后，再增强图纸、效果图和模型文件的直接理解能力

### 1.4.5 项目文件变更检测策略

| | 静默自动检测 | 手动触发更新 |
|---|---|---|
| 触发时机 | 文件保存、文件增删改 | 用户明确说"更新项目"/"刷新项目" |
| 技术实现 | `watchdog` 文件系统监听 | Agent 收到更新指令后执行 |
| 行为 | 后台静默记录变化，不弹提示 | 执行全量扫描、内容抽取、基本信息更新、`current.md` 更新、Agent 记忆更新 |
| 用户感知 | 无感知 | 可见进度和结果 |

规则：
- 后端启动后，使用 `watchdog` 常驻监听项目文件夹的文件系统事件
- 检测到文件变化时，静默更新内存中的项目文件索引，不触发任何 Agent 逻辑
- **不主动**根据文件变化做内容分析或推送提示给用户
- 仅在以下情况才执行全量更新：
  - 用户明确指令："更新项目""刷新项目""更新项目状态"
  - 用户通过对话上传文件或提及新文件，视为隐式更新指令
- 全量更新后，Agent 应在对话中简洁汇报更新结果：检测到哪些变化、更新了哪些字段、哪些字段仍然缺失

通俗理解：像微信——有人发消息它知道（自动检测），但不弹窗；你点进去看才加载内容（手动触发分析）。

### 1.4.6 项目 Agent 记忆

每个项目在 `06_agent_memory/` 下由 Agent 自动维护项目记忆文档，目标是让 Agent 下次打开项目时能无缝续接上下文。

记忆内容：

| 分类 | 内容 |
|------|------|
| 项目进度时间线 | 关键时间节点和主要工作内容摘要 |
| 设计决策记录 | 做了哪些重要决策、为什么这样选、放弃了哪些方案 |
| 已解决问题 | 过去提过的问题和 Agent 给出的建议/依据 |
| 待解决问题 | 当前仍然待处理的问题清单 |
| 对话摘要 | 每次重要对话的简短摘要 |
| 规范引用 | 本项目引用过哪些规范条文 |

运作方式：

- Agent 每次开始新对话或切换项目时，先读取 `06_agent_memory/` 了解项目历史和当前状态
- 每次重要对话结束后，Agent 自动更新记忆文档（追加决策、更新待办、记录对话摘要）
- 记忆文档使用 Markdown 格式，人类可读，也可直接用于 LLM 上下文
- 记忆不替代项目基本信息，而是补充"为什么"和"之前聊了什么"
- 如果记忆过长影响上下文窗口，Agent 自动做摘要压缩

```text
06_agent_memory/
  01_decision_log.md       # 设计决策记录
  02_problem_log.md        # 已解决 / 待解决问题
  03_conversation_log.md   # 对话摘要时间线
  04_project_timeline.md   # 项目进度时间线
  05_spec_refs.md          # 本项目引用过的规范
```

### 1.4.7 设计条件版本管理与项目回溯

#### 文件组织模式

输入资料（设计条件、任务书、地形图等）和过程文件都采用 **latest + archive** 双层结构：

```text
01_input/
  设计条件/
    latest/                   ← 始终放当前有效版本（Agent 自动维护）
      甲方设计条件.docx
      规划局出让条件.pdf
    archive/                  ← 历史版本，按日期归档
      2026-03-15/
        甲方设计条件_v1.docx
      2026-04-20/
        甲方设计条件_v2.docx
        规划局补充说明.pdf
    changelog.md              ← Agent 自动维护的变更记录

04_working/
  CAD/
    latest/                   ← 当前有效图纸（Agent 自动维护）
    archive/                  ← 历史版本，按日期归档
      2026-04-13/
      2026-04-20/
      2026-05-01/
    changelog.md              ← Agent 自动维护的版本变更记录
```

**用户操作**：只把新文件放入 `archive/日期/` 文件夹。

**Agent 操作**：自动检测新版本 → 对比内容 → 更新 `latest/` → 更新 `changelog.md`。

#### changelog.md 示例（Agent 自动维护）

```md
# 设计条件变更记录

## 2026-04-20（当前版本）
状态：已应用
变化：
- 容积率：2.5 → 3.0
- 限高：60m → 80m
影响评估：容积率提升 20%，限高增加 20m，之前基于旧条件做的方案可能需要重新评估退线和面积配比
来源文件：archive/2026-04-20/甲方设计条件_v2.docx

## 2026-03-15
状态：已被 2026-04-20 取代
内容：容积率 2.5，限高 60m，总建筑面积 80000m²
来源文件：archive/2026-03-15/甲方设计条件_v1.docx
```

#### 项目推倒重来 / 从历史版本继续

| 场景 | 用户操作 | Agent 行为 |
|------|----------|------------|
| 推倒重来 | 说"推倒重来，回到最新设计条件重新开始" | 保留所有 `archive` 历史文件不动，把 `04_working/latest/` 清空，基于当前 `01_input/latest/` 重新开始 |
| 从某个历史方案继续 | 说"从 3月15日那版方案继续做" | 把 `archive/2026-03-15/` 的内容拷贝到 `latest/`，更新 `changelog.md` 记录回退操作，但不删除任何 archive 文件 |
| 比对新旧方案 | 说"比较 3月和4月的方案差异" | 读取两个日期的 archive，分析 CAD 文件列表、说明文档差异，输出对比报告 |

**核心原则**：
- 所有历史文件永久保留，不删除
- 任何回退或重来操作都记录在 changelog.md 中
- `latest/` 永远是当前工作版本，`archive/` 是不可变历史
- 用户只管往 `archive/日期/` 放文件，Agent 负责维护 `latest/` 和 `changelog.md`

### 1.5 交互形态

- **Web 页面**（浏览器访问，localhost 部署）
- 类 ChatGPT 的对话界面
- 支持流式输出（打字机效果）
- 预留图片上传入口（为后续多模态）

## 2. 技术栈选型

### 2.1 推荐方案：Python 后端 + React 前端

| 层 | 选型 | 理由 |
|---|---|---|
| **后端框架** | **FastAPI** | 异步原生（高并发），WebSocket 原生支持（流式对话推送），Python 类型提示，自动生成 OpenAPI 文档 |
| **LLM 编排** | **LangChain** | DeepSeek-V4 兼容 OpenAI API，Agent/Tool 抽象成熟，内置 RAG 和搜索链 |
| **联网搜索** | **Tavily Search API** | 专为 AI Agent 设计的搜索 API，返回结构化结果，支持领域过滤 |
| **向量数据库** | **ChromaDB** | 轻量、嵌入式、Python 原生、零配置，存项目文档向量 + 模板向量 |
| **项目存储** | **PostgreSQL + 本地文件目录** | PostgreSQL 存项目元数据、结构化项目状态、对话记录、模板索引；原始附件和生成文件按项目目录存放 |
| **前端框架** | **React 18 + Vite** | 聊天 UI 组件生态成熟，HMR 开发体验好，后续图片标注/图纸预览扩展方便 |
| **UI 组件** | **Ant Design** | 中文生态好，Chat 组件成熟，建筑行业的专业感 |
| **部署** | **Docker Compose 本地部署** | 一键启动前端、后端、PostgreSQL、ChromaDB 等服务；本地可控，后续迁移到服务器也更顺畅 |

### 2.2 备选方案对比

#### 方案 A：纯 Python（FastAPI + Streamlit / Gradio）

| 优点 | 缺点 |
|------|------|
| 一个语言搞定全栈 | UI 定制受限，缺乏专业感 |
| 最快出 MVP（几天） | 图片标注、图纸预览难做 |
| 适合原型验证 | 长线维护性差 |

> 适合：快速验证想法，后续再重写前端

#### 方案 B：Next.js 全栈（TypeScript）

| 优点 | 缺点 |
|------|------|
| 前后端统一语言 | RAG 生态远不如 Python |
| Vercel 部署方便 | LangChain/LlamaIndex 最佳实践都在 Python |
| Server Actions 方便 | 向量搜索、文档处理库不成熟 |

> 适合：团队以 TypeScript 为主，RAG 需求简单

#### 方案 C：Python 后端 + React 前端（推荐）

| 优点 | 缺点 |
|------|------|
| RAG/AI 用 Python 最佳生态 | 前后端两种语言，需 API 约定 |
| React 做聊天 UI 最成熟 | 初期项目搭建步骤多一点 |
| 前后端独立迭代 | |
| 长期扩展性强（多模态、图纸工具） | |

> **推荐理由**：取 Python AI 生态之长 + React UI 生态之长，各自做最擅长的事。

### 2.4 本地部署形态

采用 Docker Compose 管理本地运行环境：

| 服务 | 说明 |
|------|------|
| `frontend` | React + Vite 前端页面 |
| `backend` | FastAPI 后端服务，负责对话、Agent 编排、项目读写、搜索工具调用 |
| `postgres` | PostgreSQL 数据库，存结构化项目数据、会话、模板索引 |
| `chromadb` | 向量数据库，存项目文档片段、模板片段、可复用成果片段的 embedding |
| `storage` | 本地挂载目录，存 PDF、图片、Word、Markdown、生成文件等原始附件 |

这种部署方式的好处：

- 对使用者来说接近“本地软件”，但仍保留 Web 交互体验
- PostgreSQL、ChromaDB 等依赖不污染本机环境
- 程序员朋友可以通过统一的 `docker compose up` 复现运行环境
- 后续如果要部署到 NAS、局域网服务器或云服务器，迁移成本较低

### 2.5 多模型架构设计

系统从第一天起就预留多模型扩展能力。MVP 默认使用 DeepSeek-V4 作为全局对话模型，但架构上不绑定单一模型。

#### 模型目录

```text
全局默认模型    →  DeepSeek-V4（对话、分析、工具调用）
未来可选模型    →  生图模型（如 DALL·E、Stable Diffusion API）
              →  建模/渲染 API（如 TripoSR、Meshy 等 3D 生成）
              →  多模态模型（审图、图纸理解）
              →  其他厂商 LLM（备用或对比切换）
```

#### 架构设计

```text
前端 → API → Router → ModelManager
                        ├── default_model: DeepSeek-V4（对话）
                        ├── future_models: {生图, 审图, 3D...}
                        └── model_registry: 模型注册表

             每个模型都实现统一接口：
             class BaseModel:
                 async def chat(messages) → response
                 async def chat_stream(messages) → AsyncIterator

             DeepSeekChat(BaseModel)
             ImageGenModel(BaseModel)          # 后续
             DrawingReviewModel(BaseModel)     # 后续
```

**配置方式**：`.env` 文件管理

```env
# MVP 阶段只有一个模型
DEFAULT_MODEL=deepseek-v4
DEEPSEEK_API_KEY=sk-xxx
DEEPSEEK_BASE_URL=https://api.deepseek.com

# 后续增加生图模型
IMAGE_MODEL=dalle-3
IMAGE_API_KEY=sk-xxx
IMAGE_BASE_URL=https://api.openai.com

# 后续增加审图模型
REVIEW_MODEL=gpt-4o
REVIEW_API_KEY=sk-xxx
```

#### 切换规则

- 当前对话上下文由 `DEFAULT_MODEL` 处理全部逻辑
- 后续当用户触发特定意图时（如"帮我生成效果图"），Agent 自动判断意图并路由到对应专用模型
- 模型路由对用户透明——用户不需要知道背后用了哪个模型
- 如果指定模型不可用，自动回退到 `DEFAULT_MODEL` 并提示用户

#### MVP 实现

第一版只实现 `DeepSeek-V4` 一个模型，留下 `ModelManager` 的抽象层和多模型接口，为后续扩展铺路。

## 3. 已确认工具设计

### 3.1 `websearch` 工具

#### 目标

实现一个后端工具 `websearch`，接入 Tavily 搜索引擎，供后续 Agent 在回答建筑规范、案例、前沿知识时调用。

#### 推荐接口

```python
websearch(
    query: str,
    max_results: int = 5,
    include_raw_content: bool = False,
) -> list[SearchResult]
```

#### 返回结构

```json
[
  {
    "title": "页面标题",
    "url": "https://...",
    "content": "搜索结果摘要",
    "score": 0.91
  }
]
```

#### 配置要求

- 使用环境变量 `TAVILY_API_KEY`
- 如果未配置 `TAVILY_API_KEY`，工具应返回明确错误，不静默失败
- 默认不保存搜索结果到数据库，先作为无状态工具
- 后续如需“规范引用可追溯”，再把搜索记录写入 PostgreSQL

#### 搜索偏好

- Agent 构造搜索词时应**优先搜索政府网站**，在关键词中附加 `site:gov.cn` 或 `site:.gov`
- 规范类问题优先检索住建部、各省市住建厅/规划局、自然资源局等官方发布
- Tavily 返回结果中，Agent 应优先采信 `.gov.cn` 来源的网页

#### 回答格式要求

Agent 在给出包含规范依据的回答时，**必须附带来源和使用方式**：

```text
依据来源：
- 《建筑设计防火规范》GB 50016-2014（2018年版）第5.5.18条
  → 来源：住房和城乡建设部官网 https://www.mohurd.gov.cn/xxx
  → 怎么用：本条文规定高层公共建筑疏散走道净宽不小于1.2m，
    你的走廊1.1m，不满足，需要调整到1.2m以上

- 杭州市城市规划管理技术规定（2023版）第x条
  → 来源：杭州市规划和自然资源局 http://ghzy.hangzhou.gov.cn/xxx
  → 怎么用：基地南侧临主干道，退让红线不小于10m
```

每条引用包含三个要素：**规范条文 → 来源链接 → 怎么用到当前问题**。

#### 实现位置建议

```text
src/
  backend/
    app/
      tools/
        websearch.py
      core/
        config.py
```

#### MVP 实现边界

- 只封装 Tavily 搜索
- 不直接绑定 LangChain Tool wrapper，先保留普通 Python 函数/类
- 后续 Agent 层确定后，再包装成 LangChain Tool
