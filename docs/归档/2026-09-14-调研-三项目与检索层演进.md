# 调研报告：QMD / LightRAG / RAPTOR 与本库检索层的下一步

> 日期：2026-09-14
> 性质：**调研与提案**。不覆盖 `需求.md`；采纳哪几条由人点头后再写进规格。
> 调研对象：`tobi/qmd`、`HKUDS/LightRAG`、`parthsarthi03/raptor`
> 附带：Agent 上下文经济学的第三方实证（论文与官方工程博客）
> 本次所有本项目数字都是在**真库**（3.37M 字 / 453 块 / 4 本书）上实测或从代码读出，不是估算。
> 开源对照的常备版仍在 `参考笔记.md`；本报告是它的**深化篇**，只谈检索层演进。

## 0. 结论（先说结果）

三条，每条都能落到文件和行号：

1. **现在最缺的不是"更聪明的检索层"，是"块里面没有地图"。**
   22.5% 的块超过一个 8000 字窗（102/453），最大一块 299,546 字 = **38 窗**；而 `kb_read` 只能给你窗口，块内小节（如「甘于平凡的勇气」@14830）**没有名字、点不到**。真实调用日志里 15 次失败，几乎全是 Agent 想点小节而失败——它不是找不到书，是**找到了书、进不去那一节**。

2. **四家调研一致指向：在 3.37M 字这个量级，加 RAG 换不来回答质量，只会换来新的失败面。**
   交叉证据：RAPTOR 自己的聚类消融只有 +0.8 分；SVD-RAG 用零 LLM 的确定性方案做到 MRR 0.867 vs 0.875（**317 倍快、省 85% token**）；而 QMD（一个已经在跑向量检索的项目）现在有一个**未修**的严重 bug：约 70% 的块被存成"与内容无关的常量向量"且不报错。代价是本库**全读一遍也只要约 10 美元**——省钱的地方不在这儿。

3. **该"抄"的是 QMD 的三样机制、LightRAG 的一句话、RAPTOR 的一个结构。**
   - QMD：**块内行锚点契约**（`#docid:起始行:行数`）、**强信号短路**（BM25 头名够强就别再做昂贵那一步）、**CJK 单字+短语**（他们踩了坑才改成这样，我们的二字片比他们强）。
   - LightRAG：**一个总预算，逐项扣减**（`sysprompt + 图 + 查询 + 200 buffer = 余下给正文`），以及"检索与生成在接口层可分"。
   - RAPTOR：**折叠树 / 混合粒度检索**——值钱的是"一次检索同时够到宏观节点和叶子"，不是递归摘要本身。

**一句话：先把「块内地图 + 命中分布」补齐（零新依赖、不碰死规矩），再谈别的。向量与重排按 `需求.md` 已写明的复访条件挂着，不到条件不上。**

## 1. 本库现状：先钉死"痛点到底长什么样"

讨论"要不要上 RAG"之前必须先看清现状。下面全部是本次实测（`mcp/knowledge_mcp/` + 真库），不是推测。

### 1.1 语料规模与形状

| 项 | 实测 |
|---|---|
| 书 | 4 本，453 个块（不含导读/地图），合计 **3,373,369 字** |
| 最大一本 | 毛选：396 块 / 5,679,018 字节 |
| 块大小 | 中位 **3,054 字**；最大 **299,546 字**（心理学与生活/27-参考文献） |
| 单窗（8000 字）可读完的块 | **351 / 453 = 77.5%** |
| 超过 24000 字（一次读的上限）的块 | 12 个；超过 40000 字的 5 个 |
| 全库 token 量级 | ≈ 3.4M–4.5M token（中文 ~1 token/字，tiktoken 实测 0.97–1.33） |

**推论：** 我们不是"库太大"的问题，是**块太大**的问题。77.5% 的块一块就能读完，说明"书/章为块"这个粒度整体是对的；坏在剩下那 100 多个块——它们内部**明明有天然结构**，却对 Agent 不可见。

### 1.2 块内结构是真实存在的，只是没被用起来

例：《心理学与生活》第 7 章 记忆，块内 24 个小节：

```text
什么是记忆   @1022
  记忆的功能   @1160
  记忆过程概述   @3458
记忆的短时功用   @4817
  映像记忆   @5249
  短时记忆   @6556      ← Q9「短时记忆怎么讲」的答案就在这个偏移
  工作记忆   @9315
长时记忆：编码和提取   @11785
  ...
```

《第五夜 认真的人生"活在当下"》块内 14 个小节，其中 `甘于平凡的勇气 @14830`、`人际关系之卡`——**Agent 真的去点过它们，全都失败了**：

```text
失败记录（检修/calls.jsonl，同一次会话内）
  在 book-fe981a7a 里找不到「甘于平凡的勇气」这一块。
  在 book-fe981a7a 里找不到「自由就是被别人讨厌」这一块。
  在 book-fe981a7a 里找不到「人际关系之卡」这一块。
  在 book-fe981a7a 里找不到「第五夜 认真的人生“活在当下”/甘于平凡的勇气」这一块。
  在 book-fe981a7a 里找不到「part0074」这一块。   ← 试过伪造身份
  在 book-fe981a7a 里找不到「CHP13-9」这一块。     ← 试过编编号
```

15 次失败里除了 3 次"超过整次字数顶"，**其余全是"找不到这一块"**。这不是 Agent 不会用，是**工具没给它能点的东西**——它试了 7 种叫法，包括编造 `part0074` / `CHP13-9`，就是因为它手上没有任何可用的内部地址。这是痛点①最硬的证据。

### 1.3 上下文管理：闸门是全库最硬的部分，但少一个"分布"

`kb_search` 的披露约束已经做得很彻底（`retrieve.py`）：`SEARCH_LIMIT=5`、`CHAR_CAP=8000`、`BATCH_LIMIT=5`、`TOTAL_CHAR_CAP=24000`，路标零正文。**这块不用改。**

但 `需求.md` 第 63 行写死的两件事没有落地：

> 「工具负责摆齐：**这本书命中多少块**、建议哪几块、邻块是谁」
> 「**命中分布只报数字**，不铺卷篇清单」

实测 `_format_landmarks()`（`retrieve.py:231`）只输出三栏标签、书标题、建议块、why，**没有任何计数**。而 `_df()`（`index.py:382`）本来就能算——**数据是现成的，只是没报**。

后果（真库实测）：

```text
kb_search("认识") → 返回 149 条，但格式化成路标后只剩 5 条
  实际命中：认识 150 块 / 阶级 260 块 / 合作 182 块 / 实践 99 块
  Agent 看到的：5 条，不知道还有 145 块
```

Agent 没法判断"是不是还有别处"，只能靠感觉决定停不停——**这正是痛点②的缺口：不是给多了，是该给的数字没给。**

顺带一个小缺陷：路标里的 why 会出现碎片。实测输出 `地图：能解决「意别人、不、讨厌我、该」`——`_why_bits`（`retrieve.py:176`）只按 `len<=20` 过滤，把重叠二字片全放进来了（`意别人`/`别人`/`人是不`/`不讨`/`讨厌`/`厌我`/`该`）。why 的作用是让 Agent **能否决**"不是这个"，碎片化了就否决不了。

### 1.4 成本：冷启动超目标 2 倍，热检索极快

真实检索入口实测（不是微基准）：

| 场景 | 实测 | `本轮Spec.md` §6 目标 | 判定 |
|---|---|---|---|
| 冷启动（进程内第一次 `kb_search`，含建索引） | **3,857 ms** | 冷启动「记实数，不挡」 | 记录 |
| 同一个进程第二次 | **25 ms** | search_ms ≤ 2000 | 过 |
| 线上同类查询（calls.jsonl） | 3,535 / 3,921 / 4,428 ms 冷；11–25 ms 热 | — | 一致 |

索引本身：11.4M 字符的 token 串，`sqlite3 :memory:`，无落盘。`_ensure()` 只在进程内建一次，`invalidate()` 在入库/写笔记/净化后触发——**设计是自洽的**，贵的是"每个新进程都要重付一次"。

`需求.md` 第 222 行记的"337 万字：建索引 2.5 秒"这次复现是 **3.9 秒**；不影响结论，但指标该按实测更新。

### 1.5 成本真正的去处：读，不是索引

```text
建索引                      一次性、$0（纯 CPU 3.9s）
embed 全库（假想）            一次性、$0.01–1.20（第三方定价）
RAPTOR 式摘要树（假想）       一次性、约 $1–2 + 每个窗口一次 LLM
把全库读完一遍（3.37M token） Sonnet $3/M ≈ $10
一次正常检索 + 读 2–3 窗       ≈ $0.05–0.10
```

**读一遍全库比任何索引都贵 10 倍以上。** 所以成本优化的靶心不是索引层，是**"少读、读对、别重读"**——也就是痛点①和②。三家调研在这个点上完全一致。

## 2. 三家各自到底是什么（只留能用的部分）

### 2.1 QMD — 本地混合检索 + 查询扩展 + 重排，给 Agent 的接口做得最"抠"

`github.com/tobi/qmd`（MIT，TypeScript/npm `@tobilu/qmd` v2.8.3，约 29.7k star）。**全本地、零 API**：三个 GGUF 模型（embeddinggemma-300M ~300MB、Qwen3-Reranker-0.6B ~640MB、自训的 qmd-query-expansion-1.7B ~1.1GB，合计约 2GB）跑在进程内。

它的检索链（`src/store.ts`）：

```text
1. BM25 探针（FTS5，k=20，字段权重 filepath 1.5 / title 4.0 / body 1.0）
   └─ 若头名 ≥0.85 且与第二名差距 ≥0.15 → 直接跳过下面的 LLM 扩展   ★强信号短路
2. 查询扩展（本地 1.7B）：产出 lex: / vec: / hyde: 三种类型的子查询
3. 类型路由检索：lex→只打 FTS；vec/hyde→只打向量；原查询→两边都打
4. RRF 融合（k=60）：原查询权重 2.0，扩展 1.0；头名 +0.05、2–3 名 +0.02
5. 截 40 个候选（RERANK_CANDIDATE_LIMIT=40）
6. 每个文档先挑"最佳块"再送重排（重排全文是 O(tokens)，他们写明这是关键性能教训）
7. 交叉编码器重排（Qwen3-Reranker-0.6B）
8. 位置感知混合：rank 1–3 保留 75% 检索权重，11+ 名把 60% 让给重排
```

**对 Agent 的接口**（`src/mcp/server.ts`，只有 4 个工具：`query` / `get` / `multi_get` / `status`）：

```text
Found 2 results for "auth flow":
#a1b2c3 93% docs/guide.md - Software Craftsmanship
#d4e5f6 67% notes/meeting.md - Q4 Planning
```

每条结果 = 身份 + 分数 + **300 字摘录** + **绝对行号锚点**。工具说明里直接教下一步：

> *"To read more context around a hit, call `get(file, fromLine = max(1, line - 20), maxLines = 80, lineNumbers = true)`."*

`get` 也吃 `#abc123:120:40` 这种身份格式。它的 SKILL.md 还写死：**"Snippets are only leads… Do not answer from snippets alone"**。

**要注意的两个反例（对我们重要）：**
- **它带 300 字摘录**——`需求.md` 死规矩 2 明令不许（路标里一个字的正文都不许有）。我们只借它的**行锚点契约**，不借摘录。
- **它有一个未修的严重 bug**（[issue #897](https://github.com/tobi/qmd/issues/897)）：嵌入输入触及 512 token 批量边界时，会**静默存成与内容无关的常量向量**，报测约 70% 的块受影响、"文档对自己的字面内容不可见"，且不报错。这是"加了向量就多了一个看不见的失败面"的现成证据。

**CJK 处理**：`unicode61` 把整句中文当一个 token（[issue #617](https://github.com/tobi/qmd/issues/617)），他们的修法是**每个汉字之间插空格 + 查询侧按字短语匹配**（`"中 文 合 约"`）。**没有分词、没有二字片、没有位置容忍**——因此多词中文查询必须用空格分开才有 AND 语义。**我们的"二字片+单字+语片 AND"在这个维度上比他们强**，这条要记下来：别人踩过的坑我们已经绕过了。

### 2.2 LightRAG — 双层检索 + 一张总预算表

`github.com/HKUDS/LightRAG`（MIT，Python ≥3.10，39.6k star，arXiv 2410.05779）。**注意：论文写的是 v1.0.x，`main` 已是 v1.5.7+，参数名全改过**——对着论文调参的人会踩空。

入库：1200 token 块 / 100 重叠，每块 **2 次 LLM 调用**（抽取 + 一次 gleaning），抽 `entity{name,type,description}` 和 `relation{src,tgt,keywords,description}`，按名字合并、`<SEP>` 拼描述、带 `source_id` 溯源。中文按 1 token/字算，**每 100 万字 ≈ 1800 次 LLM 调用**。

检索最有价值的两点：

**（a）双层关键词就是两个等级的检索键，不是一个分数：**

| 模式 | 走哪条 |
|---|---|
| `naive` | 只查块向量，无关键词、无图 |
| `local` | `low_level_keywords` → 实体向量 → **节点 + 其全部邻边** |
| `global` | `high_level_keywords` → 关系向量 → **边 + 其两端实体** |
| `hybrid` | local + global |
| `mix`（默认） | 上面全部 + 块向量 |

关键词由**查询时一次便宜的 LLM 调用**产出（`extract_keywords_only`，独立 KEYWORD 角色）；**调用方若能自己给 `hl_keywords`/`ll_keywords`，这次调用就省了**。默认只扩 1 跳，不做多跳游走。local/global 结果**轮询交错 + 按名字去重**，不做分数归一。

**（b）一张总预算逐项扣减**（`operate.py::_build_context_str`）：

```text
available_chunk_tokens = max_total_tokens(30000)
                       - (sys_prompt_tokens + kg_context_tokens + query_tokens + 200 buffer)
```

其中 `max_entity_tokens=6000`、`max_relation_tokens=8000`，且 `sys_prompt_tokens` 是**按真正要渲染的模板**数的。另有 `only_need_context` / `only_need_prompt` 开关——**检索与生成在接口层可以分开**，这点对我们"只回身份不回正文"是一条正面佐证。

**不能当底座的理由**（`参考笔记.md` §3.6 已列，这次验证后仍然成立）：它查询**返回成文散文**、需要**落盘的四套存储**（默认 JSON+NanoVectorDB+NetworkX，"仅适合小规模测试，不适合生产"——它自己的 README 写的）、**必须有 LLM**（README："LightRAG 对 LLM 的能力要求高于传统 RAG"），而且**没有实体消歧**（"Apple"公司/水果同名合并）、**没有置信度字段可过滤**（提示词里说有权重，代码里实际 default 1.0）。仓库里 `kg_integrity_repair` / `source_conflict_repair` / `rebuild_vdb` / 写前日志这一堆修复工具，本身就是失败模式清单。

### 2.3 RAPTOR — 结构值钱，摘要不值钱

`github.com/parthsarthi03/raptor`（Stanford，ICLR 2024，arXiv 2401.18059）。

做法：叶子按 token 切块 → 嵌入 → UMAP 降维 → GMM 聚类 → **每个簇让 LLM 写摘要** → 递归，得到一棵多级摘要树。检索两种：**树遍历**（每层按余弦选 top-k 下行）和**折叠树**（所有层的节点放进一个平面向量索引取 top-k）。论文说折叠树更好。

**本次调研最重要的发现是它自己的数据反过来削弱了它的卖点：**

- 论文附录 B 的消融：聚类对整体性能只影响 **+0.8 分**。
- 第三方 [SVD-RAG（arXiv:2607.10316）](https://arxiv.org/abs/2607.10316) 指出它"每个内部节点都要昂贵的 LLM 摘要，大规模部署成本高得不可行"，并用**确定性、零 LLM** 的 SVD 抽取式选择做对照：**MRR 0.867 vs 0.875、Recall@1 0.483 vs 0.458、建树 0.1s vs 31.7s（317 倍）、省约 85% token**。
- 代码侧还有**确认存在的 bug**：[#56](https://github.com/parthsarthi03/raptor/issues/56) 精确浮点相等比较在规模上直接 `AttributeError` 崩溃；[#52](https://github.com/parthsarthi03/raptor/issues/52) 多线程提交共享循环变量导致**丢数据**，而这在**默认路径**上（`use_multithreading=True`）。
- **没有增量添加**（`add_to_existing` 在仓库里根本不存在），文档一改就得重建树。

**所以对 RAPTOR 的正确态度是：抄它的"形"，不抄它的"料"。** 它真正值钱的是**折叠树 = 一次检索同时够到宏观节点和叶子**这个想法；而"每个内部节点必须由 LLM 写一段摘要"这一步，正是成本所在、且质量贡献最小的一步。

**关键映射：** RAPTOR 要靠聚类**造**一棵树，是因为它的输入是无结构文本。**我们的输入是 Markdown，树已经长在标题里了**——`#`/`##`/`###` 就是天然的层级，抽取成本为零、确定性、可重建、永不漂移。这就是本报告第 3 节的核心建议。

## 3. 痛点逐条拆解与解法

### 痛点①：Agent 能不能精准找到它要的内容？

**现状：书级、块级已经准；块内是黑的。**

真库实测（块内节级目录的压缩比）：

| 块 | 块字数 | 节数 | 节级目录字数 | 压缩比 |
|---|---|---|---|---|
| 心理学与生活 / 16 社会心理学 | 54,458 | 33 | 557 | **97.8×** |
| 心理学与生活 / 10 人的毕生发展 | 53,150 | 29 | 558 | 95.3× |
| 毛选 / 论持久战 | 52,513 | 22 | 464 | **113.2×** |
| 心理学与生活 / 7 记忆 | 46,186 | 24 | ~420 | ~110× |

**一个块的节级目录平均只要 400–600 字（≈300–400 token），换来块内精确跳转。** 8 个最大块全做也就 3,141 字。

**根因（写进 `需求.md` 的"不许"里了）：**

> 「只按一级标题切块（必须认到三级标题）」——`_cut_level()` 确实认到了三级，**但那是"切块"用的**。切完之后的块，内部还有 `##` 级小节（心理学与生活每章 15–35 个），**没有任何一层为阅读服务**。
> 「超长篇不预切 4K 文件，阅读用显式窗口」——这条是为了不撕篇（方案 B），但它把"块内导航"这件事**整个让给了窗口编号**。

于是 Agent 面对一个 46,186 字的块，唯一的动作是 `#1 → #2 → … → #6` 顺序扫。它确实试过更聪明的办法（点小节名），失败了 12 次。

**解法（抄 RAPTOR 的形 + QMD 的锚点契约，零新依赖）：**

1. 入库时顺便抽**块内节级目录**（只读 `#`/`##`/`###` 行 + 字符偏移，不调模型、不落额外格式）：
   ```text
   节：短时记忆  @6556   ← 便宜、确定、可重建
   ```
2. `kb_read` 支持**按节点名**：`书/<slug>/<块>#节名` 或 `书/<slug>/<块>@6556`——两种写法都吃（名字给人看，偏移给机器用；同名小节用偏移消歧）。
3. 顺序读仍保留 `#n` 窗，**不废**（方案 B 的成果不能丢）。节级是**叠加**，不是替换。
4. 节级目录**只在点名读某块时附在末尾**（像现在的"邻块"行那样），不进 `kb_search` 路标——路标仍然零正文、零清单，不违反死规矩。

这条路满足：书不改（目录是派生物）、索引仍是内存派生物、没有新依赖、没有新工具、没有隐藏状态（偏移是文件里的确定位置，不是会话游标）。**它是"结构只用来命名和导航"（死规矩 5）的完整兑现**——现在这句只落实了一半。

**顺带**：`is_nav_name()` 已经把「参考文献/术语表/索引」的正文排除出索引，但**块文件还在、还能被点名读**——`27-参考文献.md` 299,546 字 = 38 窗。这类块应当**在目录/阅读层也标注为"导航件，不必读"**，否则 Agent 可能真去点它。

### 痛点②：能不能管好 Agent 上下文，搜到就停？

**现状：闸门很硬，判断依据缺失。**

已经做对的（不该动）：只回身份、最多 5 条、路标 ≤1500/2000 字（目标）、正文零泄漏、一次最多 5 块/24000 字、单窗 8000、末尾报邻块、"工具绝不替 Agent 说读够了"。

**缺的是"我该停了吗"的判断依据。** 第三方实证站在我们这一边：

- Chroma《Context Rot》（2025-07，18 个模型）：固定任务难度只变输入长度，**每个模型都随长度退化**；1 个干扰项就有影响，4 个叠加；LongMemEval 上**聚焦提示（~300 token）在四个模型家族上全面胜过全文提示（~113K token）**。
- Databricks（arXiv 2411.03538，20 个模型）：多数开源模型的有效 RAG 区间只有 **16k–32k token**；GPT-4-0125 在 64K 后开始掉；o1-preview 是 **2K 0.582 → 64K 0.831 → 125K 0.763**（先升后降）。
- Anthropic：把上下文当"有限资源、边际收益递减"，目标是"最小的高信号 token 集合"；**Claude Code 的工具返回默认上限 25,000 token**。

**对照我们的参数**：8,000 字窗 ≈ 8–10.6k token，落在"干净区间"；5 块/24,000 字 ≈ 24–32k token，在多数模型的**有效带上沿**、且低于 Anthropic 自己的 25k 工具上限。**这组数字是合理的，不用改。**

**要补的两件事（都是 `需求.md` 已经写死、只是没实现）：**

1. **路标报命中分布**：每本书"命中 N 块"，以及全库总量。实现上 `_df()` 已经算得出来，`_format_landmarks()` 加一行即可。注意口径：**只报数字，不铺清单**（`需求.md` 原话），例如
   ```text
   1. [书] 被讨厌的勇气  身份：书/book-fe981a7a
      命中 4 块（全库 7 块）
      建议块：…
   ```
   这一行直接决定 Agent 是继续还是停——**Q11「克制题」和 Q11/Q12 这对设计的成败就在这儿。**
2. **把 8000 字窗的"还有多少"说清楚**：现在只有"下一窗 书/…/#2"，没有"共 6 窗，这是第 1 窗"。Anthropic 的工程建议是"用分页/范围/截断 + 合理默认值，并把'还有更多'明确告诉模型"。加一个 `（共 6 窗，本窗 1/6）` 是纯字符串改动。

**另外一个真正的浪费点**：大块顺序读。46,186 字的块，"读第 4 窗"这种需求现在只能靠 Agent 自己数着读过去——**有了痛点①的节级目录，这个浪费直接消失**。所以①和②是同一件事的两面。

### 痛点③：时间成本与 token 成本

**现状：冷启动 3.9s 是唯一超标项；其余都可接受。**

| 环节 | 实测/估算 | 判断 |
|---|---|---|
| 冷启动建索引 | **3,857 ms**（12 个块的插入是 11.4M token 串） | 超 `≤2s` 目标；进程每重启一次付一次 |
| 热检索 | 25 ms | 很好 |
| 建索引的钱 | $0（纯 CPU，无依赖） | 优势 |
| 读的钱 | 全库 ≈ $10；一次正常问答 ≈ $0.05–0.10 | **真正的成本中心** |
| 加向量的钱 | 一次性 $0.01–1.20（第三方定价） | 便宜，但换不到质量（见④） |
| 加重排的钱 | Voyage rerank-2.5 $0.05/1M ≈ 每次查询 $0.004；Cohere $2/1M ≈ $0.15 | 按次计费，会出现在账单上 |

**可抄的优化（按性价比排序）：**

1. **冷启动**：现在每次进程启动重建 11.4M token 串。可做的最小改动是**只在磁盘上留一份"派生缓存"**——但 `需求.md` 第 221 行明写"索引只在进程内存，不落盘"，`验收标准.md` 第 111 行还有"硬盘上不出现索引文件"的红线。**所以这条要么不动，要么先改规格**，不能偷偷做。（可变通的方向：把冷启动从"首搜"挪到"进程启动时后台预热"，Agent 首次检索就不用等——但这仍属产品决策，见第 4 节。）
2. **QMD 的强信号短路**：头名够强就别再做昂贵那一步。我们目前**每次检索都两路都跑**（死规矩 8 明确要求"两路都跑，不平均分"）——所以这条不能照抄。但可以抄它的**精神**：地图通道的"生活题兜底"（`_life_fallback`，全库扫地图逐字数片）只在两路都空时才跑，已经是这个思路了，方向对。
3. **QMD 的 LLM 缓存**：`llm_cache` 按 `(操作, 参数)` 做 sha256，rerank 按**块文本**缓存（跨文件相同块只算一次），只留最近 1000 行。我们没有 LLM 调用，暂时用不上；但**"内容寻址"**这个思路可以用在节级目录上——目录由块内容决定，块没改就不用重算。
4. **读得少**：见痛点①②。省下的钱比上面三条加起来都多。

### 痛点④：通用 Agent 知识库该不该上 RAG？什么时候可以上？

这是四个问题里最需要分清概念的一个。**"RAG"被混着说成了三件事，它们的答案不一样：**

| 被混为一谈的三件事 | 我们的态度 |
|---|---|
| **(a) 合成式检索**：向量/重排/扩展，为了"词对不上也能召回" | **暂不做**。地图通道就是我们的语义层（见下） |
| **(b) 管线自动化**：代码把检索+组装+生成一条龙干完，给模型一段成文上下文 | **不做，且与产品锚点冲突**。"代码焊步骤，Agent 干活"、正本是文件、索引是派生物——RAG 管线要的是"检索即答案" |
| **(c) 索引层**：把 Markdown 变成别的副本以换取检索速度/能力 | **不做**。正本永远是 Markdown，索引只在内存 |

**"地图通道"其实已经是一次 RAG，只是没有向量。** `地图.md` 的「能解决什么」是**入库时编译好的一份问题清单**，检索时拿它当第二个检索面——这正是 RAPTOR/LightRAG 想用向量+图达到的"跨词表召回"，只不过我们的桥梁是**人话问题**而不是向量空间。

**本次实测验证了这个桥梁有效（重要）**：拿地图里已有问题做"问句—问题"覆盖度匹配（纯二字片重叠，零依赖零模型）：

| 查询 | 库里地图的问题 | 覆盖度 | 结果 |
|---|---|---|---|
| 我总是很在意别人是不是讨厌我，该怎么办 | 总是在意别人是不是讨厌我该怎么办 | 1.00 | ✓ 对 |
| **对别人怎么看我这件事很不安** | 别人看我不顺眼时要不要改自己 | 0.33 | ✓ 对（改述） |
| **怎么做自己才不怕别人说闲话** | 怕被别人讨厌还想做自己怎么办 | 0.40 | ✓ 对（改述） |
| **总觉得自己不如别人** | 总觉得自己不行却又好强怎么办 | 0.71 | ✓ 对（跨书，自卑与超越） |
| 什么是短时记忆 | 短时记忆是怎么讲的、怎么记才记得住 | 1.00 | ✓ 对 |
| 怎么用 PyTorch 训练神经网络 | — | 0.00 | ✓ 空（负样本 Q6 保持） |

**6 个改述/跨书查询全对，负样本仍然空。** 当然这不是万能的——`人为什么会做梦` 覆盖度 0.00（地图没收录这个问法），但那一题**字面通道本来就能中**（`梦` 命中 61 块）。两个通道恰好互补：**字面强的题地图不用管，字面弱的题地图顶上。**

**结论：现在不需要上向量。** 地图通道已经把"词对不上"这件事吃掉了大部分，成本是 $0、失败面是零。

**什么情况下才该上？给三个可判定的触发条件**（对应 `需求.md` 第 248 行"There is a revisit condition"的精神，把它写具体）：

1. **地图覆盖不住了**：入库的书数量上到几十本、地图「能解决什么」的条目破千，人工/Agent 维护的问题清单开始互相冲突或漏项，且**实测有 ≥20% 的生活题两路都空**（现在 Q13 是靠地图过的）。
2. **规模触发**：全库字数到 **千万字量级**（`需求.md` 第 223 行原话）。现在 3.37M，还有 3 倍空间。到那时的第一个动作应该是**把索引落盘**（仍然是可扔的派生物），而不是上向量——因为那是延迟问题，不是召回问题。
3. **真·同义失败被坐实**：先攒一批"字面 + 地图都空、但内容确实在库里"的题（像 `验收标准.md` 第三节 W1–W20 那样先写死期望），**用数据证明**向量能救回来。上之前先回答：QMD 的 #897 那种"静默存坏向量、70% 受影响、不报错"的失败模式，我们有没有能力发现和验证？（这个问题本身就是一道闸。）

**还有一笔没人算的账**：加了向量/图之后，**索引就从"内存里可扔的派生物"变成"必须落盘、必须和正本同步、会过期、会漂移"的第二份真相**。LightRAG 仓库里那一整套 `kg_integrity_repair` / `source_conflict_repair` / `rebuild_vdb` / 写前日志，就是这笔账的账单。我们要为它准备多少测试和维护成本？——这比 embedding 的 $0.01 贵得多。
